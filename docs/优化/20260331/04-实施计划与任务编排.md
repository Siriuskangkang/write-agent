# 实施计划与任务编排

## 一、任务依赖分析

### 1.1 依赖关系图

```
LLM 抽象层改造
    ↓
体例优化（检查+注入）

体例编辑功能（独立）
```

**依赖说明：**
- 体例优化需要等 LLM 抽象层完成（因为要修改 AgentService）
- 体例编辑功能完全独立，可以并行

---

## 二、实施方案对比

### 方案 A：顺序实施（推荐）

**优点：**
- 代码质量可控
- 便于测试和调试
- 避免代码冲突
- 每个阶段都有明确的验收标准

**缺点：**
- 耗时较长（5-7小时）

**实施顺序：**
1. LLM 抽象层改造（2-3小时）
2. 体例编辑功能（1-2小时）
3. 体例优化（2-3小时）

### 方案 B：使用 AgentTeam 并行

**优点：**
- 可以并行处理独立任务
- 理论上更快

**缺点：**
- 多个 agent 可能产生代码冲突
- 质量难以保证
- 调试困难
- 需要额外的协调成本

**团队结构：**
```
Team Lead (我)
  ↓
├── Agent 1: LLM 抽象层
├── Agent 2: 体例编辑功能（并行）
└── Agent 3: 体例优化（等待 Agent 1）
```

---

## 三、推荐方案

**建议采用方案 A：顺序实施**

**理由：**
1. 这些改动都涉及核心功能，需要仔细审查
2. LLM 抽象层改造风险较高，需要充分测试
3. 体例优化依赖 LLM 抽象层，必须等待
4. 虽然体例编辑功能可以并行，但单独并行一个任务意义不大

---

## 四、详细实施步骤

### 阶段 1：LLM 抽象层改造（2-3小时）

**步骤：**
1. 创建 LLM 模块目录结构
2. 实现接口和工厂
3. 实现 Anthropic Provider
4. 实现 DeepSeek Provider
5. 修改 AgentService
6. 修改 AgentModule 和 AppModule
7. 安装依赖 `npm install openai`
8. 测试 Anthropic 模式
9. 测试 DeepSeek 模式

**验收标准：**
- [ ] 设置 LLM_PROVIDER=anthropic，生成目录成功
- [ ] 设置 LLM_PROVIDER=deepseek，生成目录成功
- [ ] 两种模式输出质量符合预期

### 阶段 2：体例编辑功能（1-2小时）

**步骤：**
1. 创建 StyleTemplateEdit 组件
2. 修改容器组件支持 edit 模式
3. 修改 Preview 组件添加编辑按钮
4. 添加前端 API 方法
5. 测试编辑流程

**验收标准：**
- [ ] 可以点击编辑按钮进入编辑模式
- [ ] 可以修改所有体例字段
- [ ] 保存后返回预览
- [ ] 确认后应用到项目

### 阶段 3：体例优化（2-3小时）

**步骤：**
1. 在 StyleTemplateService 添加 getProjectActiveTemplate
2. 修改 ChatPanel 添加生成前检查
3. 修改 ContentService 注入体例上下文
4. 修改 directory.chain.ts 接收体例
5. 修改 outline.chain.ts 接收体例
6. 修改 content.chain.ts 接收体例
7. 测试完整流程

**验收标准：**
- [ ] 未设置体例时生成目录，弹窗提示
- [ ] 设置体例后生成目录，包含体例特征
- [ ] 生成的内容符合体例规范

---

## 五、风险控制

### 5.1 回滚策略

每个阶段完成后：
1. 提交 git commit
2. 标记版本号
3. 如果下一阶段出问题，可以回滚

### 5.2 测试策略

每个阶段都要：
1. 单元测试（如果有）
2. 手动功能测试
3. 回归测试（确保不影响现有功能）

---

## 六、时间估算

| 阶段 | 预估时间 | 缓冲时间 | 总计 |
|------|---------|---------|------|
| LLM 抽象层 | 2小时 | 1小时 | 3小时 |
| 体例编辑 | 1小时 | 1小时 | 2小时 |
| 体例优化 | 2小时 | 1小时 | 3小时 |
| **总计** | **5小时** | **3小时** | **8小时** |

---

## 七、结论

**推荐采用顺序实施，不使用 AgentTeam。**

原因：
- 改动涉及核心功能，需要谨慎
- 依赖关系明确，并行收益不大
- 质量和稳定性优先于速度

# 教材编写Agent 项目检查计划

## 1. 目标

本计划用于指导后续 AI 按照开发文档与现有代码，对项目进行系统性检查、修正和完善。目标不是一次性“重写项目”，而是按优先级逐步完成：

1. 修复阻塞性工程问题
2. 对齐开发文档、接口契约与现有实现
3. 补齐缺失功能与联调链路
4. 建立基本可验证的测试与验收基线

## 2. 检查依据

以以下文档和代码为准：

- `开发文档/教材编写Agent_前端开发方案.md`
- `开发文档/教材编写Agent_后端开发方案.md`
- `开发文档/教材编写Agent_接口与数据库契约.md`
- `frontend/`
- `backend/`

## 3. 当前实现快照

### 3.1 已落地的主干能力

- 后端已经按模块拆分出 `auth`、`project`、`file`、`chunk`、`retrieval`、`agent`、`content`、`citation`、`export`、`session`
- 前端已经有登录页、注册页、项目列表、工作台、素材页
- 后端全局前缀、Cookie 鉴权、Swagger、TypeORM、Bull 已接入
- 已有数据库初始迁移，核心实体基本齐全
- 正文生成、改写、扩写、精简已具备基础 SSE 流式接口
- 素材上传、解析、重解析、删除、导出任务已具备基础接口

### 3.2 已确认的高优先级风险

- 前端生产构建失败：`frontend/src/hooks/useSSE.ts` 存在 TypeScript 类型错误
- 前端页面与文档不一致：缺少 `/projects/[id]/settings`、`/settings`
- 前端会话流未真正接入 `SessionModule`，当前聊天记录主要保存在本地 Zustand
- 目录/大纲/正文链路存在“能跑但未完全按契约落库/回读”的风险
- `CitationController` 使用 `AuthGuard('jwt')`，但代码中未看到对应 `JwtStrategy`
- 前端 SSE 直接拼接后端绝对地址，和文档要求的同源 `/api/*` 存在偏差
- 测试体系基本未建立：前端无业务测试，后端仅保留 Nest 默认示例测试

### 3.3 当前已知工程基线

- `backend` 执行 `npm run build` 已通过
- `frontend` 执行 `npx next build` 失败，报错位置：`frontend/src/hooks/useSSE.ts`

## 4. 执行原则

后续 AI 按本计划执行时，必须遵守：

1. 先修复阻塞性问题，再做功能补齐
2. 每次只处理一个明确主题，不要跨模块大面积同时修改
3. 同一主题的检查、定位、修复应尽量由同一个主执行 AI 完成，不按“分析→开发→测试”做流水线拆分
4. 验证任务可以独立拆给验证型 AI，但仅限黑盒验收，不负责设计方案和改代码
5. 每修复一个主题，必须同步做最小自检；完成一个阶段后，再做阶段级独立验证
6. 验证必须有明确标准，禁止使用“看起来正常”“应该可以”之类模糊结论
7. 验证必须覆盖正向场景、边界场景、负项场景，尤其是鉴权失败、空输入、非法输入、异常中断
8. 发现“文档、接口、代码”三者冲突时，优先以开发文档和数据库契约为准，再评估现有实现是否需要调整
9. 任何涉及接口字段、状态枚举、SSE 事件、主键命名的修正，都必须同时检查前后端

## 5. 执行分工

### 5.1 主执行 AI

职责：

- 阅读文档和代码
- 确认问题根因
- 直接完成代码或文档修正
- 做最小自检并说明剩余风险

适用范围：

- 同一功能的分析、设计、修复
- 需要理解内部实现细节的联动修改
- 跨文件但共享上下文很强的改动

### 5.2 验证型 AI

职责：

- 按既定标准执行构建、测试、联调、接口核验、负项测试
- 仅从黑盒结果判断是否通过
- 输出失败项、复现步骤和证据

适用范围：

- 运行前后端构建
- 按接口契约核对响应结构
- 核对 SSE 事件类型、顺序和异常表现
- 跑业务链路回归
- 跑边界和负项测试

禁止事项：

- 替主执行 AI 做架构决策
- 在未理解根因前直接改代码
- 用主观描述代替可执行验证标准

### 5.3 验证铁律

每个验证任务必须满足：

1. 有明确对象：验证哪个模块、哪个接口、哪个页面、哪条链路
2. 有明确标准：通过条件必须可执行、可观察、可复现
3. 有完整覆盖：至少包含正向场景、边界场景、负项场景
4. 有结果证据：命令结果、接口响应、页面行为、错误信息、数据库变化至少覆盖其一
5. 未实际运行时不得标记为“已验证”

## 6. 覆盖矩阵

后续所有检查与验证，必须至少覆盖以下维度，不能只验证“主流程能跑通”：

### 6.1 输入维度

- 空输入
- 最小合法输入
- 最大合理输入
- 超长文本
- 特殊字符
- 中英文混合内容
- 非法枚举值
- 非法 UUID
- 缺失必填字段
- 多字段组合冲突

### 6.2 用户行为维度

- 首次进入系统
- 已登录用户刷新页面
- 连续重复点击
- 生成中主动停止
- 生成完成后再次操作
- 返回上一页后再进入
- 长时间停留后继续操作
- 多标签页并行操作同一项目

### 6.3 数据状态维度

- 全新空项目
- 有项目无素材
- 有素材但未解析完成
- 有素材且部分解析失败
- 已生成目录但无大纲
- 已生成大纲但无正文
- 已有历史正文版本
- 存在低置信度引用
- 存在素材不足标记

### 6.4 异常与失败维度

- 未登录访问
- 登录过期
- refresh 失败
- 网络超时
- SSE 中途断流
- 后端 4xx
- 后端 5xx
- 队列任务失败
- 文件解析失败
- 导出文件不存在

### 6.5 并发与一致性维度

- 同一操作重复提交
- 同一资源并发保存
- 先停止再重试生成
- 一个项目内连续多次生成
- 删除后继续访问旧资源
- 重解析期间查询旧结果

### 6.6 真实使用场景维度

- 教师首次创建教材项目并从零开始编写
- 用户先批量上传素材，再分批等待解析
- 用户目录生成后只写部分章节
- 用户在正文生成后多次改写、扩写、精简
- 用户发现引用不足并回到素材页补料
- 用户第二天重新进入项目继续写作
- 用户在导出前检查引用和版本状态

## 7. 检查总顺序

建议后续 AI 严格按以下顺序推进：

1. 工程可运行性基线
2. 页面与路由契约
3. 后端接口与鉴权契约
4. 数据库与实体契约
5. 核心业务链路联调
6. 测试、日志、错误处理与部署细节

## 8. 详细检查计划

### 阶段 A：工程基线与阻塞问题

#### A1. 构建与脚本检查

检查项：

- 前端是否可通过 `next build`
- 后端是否可通过 `npm run build`
- 前后端脚本是否完整
- 前端是否具备真实测试脚本，而不是占位脚本

当前重点：

- 优先修复 `frontend/src/hooks/useSSE.ts` 的类型错误
- 检查 `frontend/package.json` 中 `test` 仍为占位命令的问题

通过标准：

- 前后端构建都能通过
- 关键脚本命名清晰，至少包含 `build`、`dev`、`test` 的合理定义

产出：

- 一份最新的构建结果记录
- 一份前后端脚本整改清单

独立验证要求：

- 验证型 AI 必须实际运行前端、后端构建命令并记录退出结果
- 必须明确记录失败位置，不能只写“构建失败”
- 负项验证需覆盖缺失脚本、类型错误、测试脚本占位这类情况
- 边界验证需覆盖冷启动构建、增量修改后再次构建、仅前端/仅后端单独构建

#### A2. 运行环境与配置检查

检查项：

- `.env.example` / `.env.local.example` 是否覆盖必要变量
- `NEXT_PUBLIC_API_URL`、数据库、Redis、JWT、LLM 配置是否自洽
- `docker-compose.yml`、`nginx/nginx.conf`、`ecosystem.config.cjs` 是否与当前实现一致

通过标准：

- 新环境按示例变量可以启动
- Nginx 转发路径、Next 重写、Nest `globalPrefix` 一致

---

### 阶段 B：文档契约对齐检查

#### B1. 页面路由对齐

按前端方案逐项核对：

- `/login`
- `/register`
- `/projects`
- `/projects/[id]`
- `/projects/[id]/files`
- `/projects/[id]/settings`
- `/settings`

当前发现：

- 已有：登录、注册、项目列表、工作台、素材页
- 缺失：项目设置页、个人设置页
- `/projects/[id]/files` 当前仅做跳转到 `/materials`

检查动作：

- 判断缺页是未实现、废弃设计，还是已迁移到其他路径
- 若未实现，先补页面骨架和最小可用交互，再接业务逻辑

通过标准：

- 文档中列出的页面均可访问
- 页面职责和文档描述一致

边界与真实场景补充：

- 未登录直接访问工作台、素材页、设置页
- 项目不存在或 ID 非法时的页面表现
- 项目为空、目录为空、无引用时的空态是否合理
- 浏览器刷新、返回、重复进入页面时状态是否稳定

#### B2. 接口路径与响应格式对齐

按契约检查所有控制器：

- 路径是否统一挂在 `/api`
- JSON 响应是否统一 `success/data/message/error_code`
- 分页接口是否统一 `items/total/page/page_size`
- 鉴权接口是否基于 Cookie 而非 Bearer Token

重点核对模块：

- `auth.controller.ts`
- `project.controller.ts`
- `file.controller.ts`
- `content.controller.ts`
- `citation.controller.ts`
- `session.controller.ts`
- `export.controller.ts`
- `retrieval.controller.ts`

特别关注：

- 是否有接口未使用 `ok()` / `paged()` 包装
- Swagger `ApiCookieAuth` 是否挂全
- 参数命名是否稳定使用 `project_id`、`result_id`、`node_id` 体系

边界与真实场景补充：

- 必填字段缺失、字段类型错误、超长字段、非法枚举值
- 无权限访问其他项目资源
- 删除后的资源再次查询
- 同一接口短时间重复调用

#### B3. SSE 契约对齐

按契约检查生成类接口是否统一输出：

- `meta`
- `token`
- `citation`
- `done`
- `error`
- `heartbeat`

当前已知风险：

- 目录、大纲生成的 `result_id` 为时间戳型临时值，不是稳定 UUID
- 内容流里未明显实现 `heartbeat`
- 内容流里引用事件是否真正发出，需要逐条验证
- 前端 `useSSE` 对事件模型的处理不够稳健，且已导致构建错误
- SSE 契约目前更偏字段层，对“何时到达前端、是否被代理缓冲、页面是否实时消费”约束不足

通过标准：

- 所有生成类接口事件类型一致
- 前端能正确处理中断、异常、done、引用增量
- 中止后状态以服务端结果为准

独立验证要求：

- 验证型 AI 必须记录至少一条完整 SSE 事件序列
- 必须验证中断场景、异常场景、空返回场景
- 不能只根据代码阅读推断 `citation`、`heartbeat` 已实现，必须以实际结果为准
- 必须验证短内容、长内容、慢速输出、异常中途终止四种流式表现
- 必须记录 `meta` 到首个 `token` 的时间、`heartbeat` 实际间隔、`done` 时间，不能只记录事件顺序
- 必须验证真实浏览器中 `ReadableStream` 是否持续收到增量 chunk，而不是只在请求结束后一次性看到完整响应
- 必须验证真实代理链路：浏览器 -> 前端开发服务器/网关 -> `/api` 转发 -> 后端，不能只用直连后端结果替代端到端结论
- 必须至少覆盖两条负例：`60s` 内无数据触发超时、首 `token` 延迟但 `heartbeat` 正常时前端不应误判失败

### 阶段 C：后端模块专项检查

#### C1. AuthModule

检查项：

- 注册、登录、刷新、退出、改密、`/auth/me` 是否完整可用
- Access Token / Refresh Token 是否都通过 httpOnly Cookie 返回
- Refresh Token 是否只存 hash
- Cookie 路径、过期时间、清理逻辑是否一致

重点风险：

- 检查 refresh 路径、cookie path 与前端刷新调用是否一致
- 检查 CORS + Cookie 在开发与部署环境是否可用

通过标准：

- 登录后刷新页面仍可恢复登录态
- 过期 access token 能静默 refresh
- 退出登录后 Cookie 与 refresh token 均失效

边界与真实场景补充：

- 重复登录
- 修改密码后旧登录态失效
- refresh 接口单独访问
- 多标签页同时触发登录失效恢复

#### C2. ProjectModule

检查项：

- 项目 CRUD 是否完整
- 项目状态 `GET/PUT /projects/:id/state` 是否前后端都接入
- 排序、分页、关键字搜索是否符合文档
- 默认状态与 `project_states` 初始化是否正确

重点风险：

- 前端 `projectService` 已有更新接口，但页面未见完整设置/编辑入口
- 文档中的“最近编辑优先排序”需验证是否与 `updated_at DESC` 一致

#### C3. FileModule + ParseWorker

检查项：

- 上传、列表、详情、解析结果、重解析、删除是否可用
- 支持格式是否与文档一致：`pdf/docx/pptx/md/txt`
- 文件上传后是否一定入队解析
- 重解析时是否正确清理 `documents/chunks/citations`

重点风险：

- 检查是否对非法扩展名做限制
- 检查上传接口是否校验 project 归属
- 检查删除时数据库与物理文件是否一致
- 检查 ParseWorker 是否覆盖全部声明的解析器

通过标准：

- 素材全链路从上传到解析完成可闭环
- 失败文件可重试
- 删除/重解析不会留下脏数据

边界与真实场景补充：

- 上传空文件、超大文件、非法格式文件
- 同名文件重复上传
- 批量上传时部分成功部分失败
- 解析中删除文件
- 重解析后再次进入列表和详情页

#### C4. ChunkModule + RetrievalModule

检查项：

- 切块、关键词、`search_terms`、向量字段是否真正写入
- 检索是否支持关键词召回与混合排序
- embedding 缺失时是否有合理降级

当前已知情况：

- `semanticSearch()` 依赖 `getQueryEmbedding()`，当前返回 `null`
- 这意味着语义检索很可能仍是占位逻辑

通过标准：

- 至少 MVP 的关键词召回可稳定工作
- 若语义检索未完成，需要明确标记为 Phase 2 或补完实现

边界与真实场景补充：

- 空查询
- 极短查询词
- 超长查询词
- 中英文混合查询
- 素材量较少和较多时的返回差异

#### C5. ContentModule + AgentModule

检查项：

- 目录生成、大纲生成、正文生成、改写、扩写、精简是否全部能闭环
- 是否正确落库 `writing_results`、`content_versions`、目录版本、大纲版本
- 章节/节 ID、标题、版本号是否按契约保存
- 中断、失败、完成状态是否正确写入

重点风险：

- 目录/大纲生成目前更像“流式输出文本”，需要确认是否稳定保存为结构化版本
- `ChatPanel` 中目录保存依赖前端解析 AI 返回 JSON，存在脆弱性
- `saveDirectory` 当前固定传 `base_version_number: 1`，需确认是否支持版本并发控制
- `generateContent()` 中 `citation` 事件与引用落库链路需重点验证
- `getWritingResult()` 的权限校验与字段完整性需确认

通过标准：

- 目录、大纲、正文都能从“生成”进入“可回读”
- 版本信息真实可追踪，不依赖前端临时状态

边界与真实场景补充：

- 无素材直接生成
- 有素材但解析未完成时生成
- 生成目录后反复生成新版本
- 先生成正文再做改写/扩写/精简链式操作
- 生成中止后再次生成
- 刷新页面后读取最新结果和版本链

#### C6. CitationModule

检查项：

- 正文引用能否按 `paragraph_key` 正确存取
- 获取正文引用、单条引用、素材不足标记是否可用
- 低置信度引用与 `unsupported` 使用类型是否能被前端感知

当前高风险问题：

- `citation.controller.ts` 使用 `AuthGuard('jwt')`
- 当前代码中未看到 `JwtStrategy`，大概率与项目现有 Cookie Guard 不一致

处理要求：

- 统一鉴权方式，避免同一项目存在两套 JWT 守卫实现

边界与真实场景补充：

- 无引用结果查询引用
- 查询不存在的 `resultId` / `citationId`
- 低置信度与 `unsupported` 类型在前端的实际表现

#### C7. ExportModule

检查项：

- 创建导出任务、查询状态、下载文件是否闭环
- 导出队列与 worker 是否能产出真实文件
- Word / Markdown 生成内容是否正确拼装目录、正文、引用

重点风险：

- `export.service.ts` 只负责建任务与取文件，需确认 worker 是否真的落地完整生成逻辑
- 导出成功状态、下载 URL、磁盘文件存在性要一起验证

边界与真实场景补充：

- 无正文内容时导出
- 仅导出部分章节
- 导出完成后重复下载
- 导出过程中离开页面再返回

#### C8. SessionModule

检查项：

- 创建会话、会话列表、消息分页、删除会话是否可用
- 工作台是否真实使用会话接口，而不是仅用前端本地状态
- 多轮上下文是否按文档要求保留最近 20 轮

当前已知风险：

- 前端聊天面板未见真实会话创建、消息持久化、消息回读
- 这意味着文档要求的“会话上下文”很可能尚未落地

边界与真实场景补充：

- 空会话
- 大量消息分页
- 删除会话后刷新页面
- 多会话切换

### 阶段 D：数据库与实体一致性检查

#### D1. Migration 与 Entity 一致性

检查项：

- 所有实体字段是否与迁移脚本一致
- 枚举值、默认值、索引、外键、唯一约束是否匹配
- `project_states.current_directory_version_id` 是否真正建立关联约束或通过应用层维护

重点检查表：

- `users`
- `refresh_tokens`
- `projects`
- `project_states`
- `source_files`
- `documents`
- `chunks`
- `sessions`
- `messages`
- `directory_versions`
- `outline_versions`
- `writing_results`
- `content_versions`
- `citation_maps`
- `export_jobs`
- `user_settings`

#### D2. 主键与命名一致性

检查项：

- 对外返回字段是否稳定
- 前端类型定义与后端实体序列化后的字段是否一致

重点风险：

- 文档大量使用 `project_id`、`result_id`、`node_id`
- 前端 TypeScript 类型里部分资源仍以 `id` 表示主键
- 需要判断这是“内部实体字段命名”还是“接口输出契约偏移”

通过标准：

- 对外 API 的主键字段命名统一，不给前端造成二义性

边界与真实场景补充：

- 新建资源响应
- 查询详情响应
- 分页列表响应
- SSE 事件载荷
- 删除后错误响应

### 阶段 E：前端专项检查

#### E1. 认证与路由守卫

检查项：

- `AuthGuard` 是否正确初始化登录态
- 401 后刷新逻辑是否只重放一次请求
- 刷新失败是否可靠跳转登录页
- 未登录访问受保护页面是否稳定重定向

重点检查：

- `frontend/src/services/api.ts`
- `frontend/src/components/common/AuthGuard.tsx`
- `frontend/src/services/authService.ts`

#### E2. 项目列表与项目管理

检查项：

- 项目列表分页、排序、删除确认、新建项目是否完整
- 是否具备项目编辑入口
- 是否能进入工作台、素材页、设置页

通过标准：

- 文档列出的项目管理动作都能在前端触发并成功调用后端

边界与真实场景补充：

- 项目名为空
- 项目名超长
- 连续快速创建多个项目
- 删除当前正在访问的项目

#### E3. 素材页

检查项：

- 批量上传、轮询解析、删除、重解析、错误提示是否完整
- 支持格式展示是否与后端一致
- 表格字段是否与契约一致

重点风险：

- 当前页面有轮询，但未见“查看解析结果”入口
- 文件类型接受列表含 `.doc`，但后端文档定义的是 `docx`

#### E4. 工作台三栏布局

检查项：

- 左栏目录树、中栏消息/正文、右栏出处面板是否职责清晰
- 顶部项目信息、状态、导出按钮是否正常
- 目录选择是否能正确驱动章节/小节上下文

重点风险：

- 当前工作台以聊天形式承载目录/正文，但文档要求还有大纲与结构化展示
- 大纲区域是否缺失独立展示层，需要明确

#### E5. SSE 与流式渲染

检查项：

- `useSSE` 的事件解析是否健壮
- 中止逻辑是否保留已生成内容
- `done/error/abort` 后的状态是否一致
- 是否通过同源 `/api` 访问，而不是绕过 Next 代理

当前高优先级问题：

- `useSSE.ts` 导致前端构建失败
- 事件类型处理依赖运行时补字段，类型设计不稳

通过标准：

- 构建通过
- 流式过程中不出现类型错误、状态错乱、重复消息、引用丢失

边界与真实场景补充：

- 用户快速多次点击“生成”
- 停止后再次生成
- 流式过程中切换页面或刷新页面
- 长文本渲染与引用增量同时出现

#### E6. 编辑器与内容状态

检查项：

- `editorStore`、`chatStore`、`projectStore`、`authStore` 是否职责清晰
- 当前目录版本、当前正文结果、引用面板数据是否可回放
- 页面刷新后是否能从后端恢复必要状态

重点风险：

- 当前大量状态停留在前端内存中
- 页面刷新后工作台上下文可能丢失

#### E7. 出处与引用面板

检查项：

- 引用列表字段是否齐全
- 低置信度、`unsupported`、素材不足警告是否显著
- 点击引用是否能查看原文片段

当前风险：

- 前端展示面板已存在，但要确认是否真正拿到后端 `citation` 数据

#### E8. 导出流程

检查项：

- 导出弹窗参数是否与后端 DTO 一致
- 轮询导出状态是否可靠
- 完成后下载是否成功

#### E9. 设置页

检查项：

- 项目设置页是否实现项目级默认参数维护
- 个人设置页是否实现昵称、密码、默认写作设置
- 后端是否存在对应 API 与数据表支撑

当前结论：

- 文档要求明确，但现有前后端均未见完整落地，必须列为缺口项

边界与真实场景补充：

- 项目设置未保存直接离开
- 个人设置修改密码、昵称、默认字数/风格
- 设置变更后回到工作台是否生效

### 阶段 F：联调与端到端流程检查

按真实业务链路逐条回归：

1. 注册并登录
2. 创建项目
3. 上传素材
4. 等待解析完成
5. 生成目录
6. 选择章节生成大纲
7. 选择小节生成正文
8. 查看引用和素材不足提示
9. 执行改写、扩写、精简
10. 导出 Markdown
11. 导出 Word
12. 刷新页面后恢复项目状态

每条链路都要记录：

- 请求接口
- 返回数据
- 前端展示
- 数据库变化
- 是否符合文档预期
- 首个 `meta` 时间、首个 `token` 时间、最终 `done/error` 时间
- 请求是否经过真实页面访问路径和代理链路，不能只记录接口直连结果

通过标准：

- 至少一条完整教材生成链路从头到尾无阻塞

独立验证要求：

- 验证型 AI 必须按顺序跑完整链路并逐步记录结果
- 任一步骤未实际执行，不得标记整条链路通过
- 必须至少包含一条负项链路，例如未登录访问、无素材直接生成、非法 ID 请求
- 生成类链路必须额外验证 UI 状态切换：点击生成后出现“正在思考...”，收到首个 `token` 后切到流式正文/目录，完成后退出流式状态
- 对目录、大纲、正文三类 SSE 至少各保留一条浏览器级证据：Network 事件流、页面截图或 DOM 断言、控制台关键日志
- 至少执行一次慢速流验证：人为制造首 `token` 延迟或上游慢响应，确认前端 heartbeat、重连、错误提示与设计一致

真实使用场景清单：

1. 新用户首次使用：
   注册、登录、创建项目、上传首批素材、生成目录
2. 素材驱动写作：
   批量上传多种格式素材、等待解析、选择章节生成大纲和正文
3. 分阶段编写：
   先只生成目录和部分章节，退出后第二次进入继续写作
4. 修改迭代：
   对同一正文依次执行改写、扩写、精简，并核对版本链
5. 补料修正：
   发现素材不足提示后返回素材页补传文件，再次生成正文
6. 导出交付：
   导出 Markdown、导出 Word、返回下载、再次下载历史导出
7. 中断恢复：
   生成中主动停止、刷新页面、重新进入项目、确认已保存状态
8. 异常访问：
   未登录访问、非法 ID、删除后的资源访问、过期登录态恢复失败

### 阶段 G：质量与非功能性检查

#### G1. 错误处理

检查项：

- 前后端错误提示是否可理解
- SSE 异常、解析失败、导出失败、鉴权失败是否有明确反馈
- 是否存在仅 `console.log` 无用户反馈的情况

#### G2. 日志与调试痕迹

检查项：

- 清理明显调试日志
- 后端是否使用结构化日志
- 前端是否保留过多开发期 `console.log`

#### G3. 安全性

检查项：

- Cookie 配置是否包含 `httpOnly`、`sameSite`、`secure` 的合理策略
- 上传文件是否限制类型和大小
- 下载接口是否做项目归属校验
- 所有受保护接口是否统一鉴权

#### G4. 测试

检查项：

- 后端是否补齐模块级单测与关键 e2e
- 前端是否补齐至少页面/Hook/服务层测试
- SSE 是否有单独测试分层：解析单测、后端延迟/断流集成测试、浏览器级流式 E2E
- 测试是否覆盖真实代理链路，而不是只覆盖前后端直连
- 测试是否覆盖时序断言，而不是只断言最终返回内容

当前已知情况：

- 后端测试仍是默认 `Hello World`
- 前端业务测试为空

最低要求：

- Auth、Project、File、Content、Export 至少覆盖关键主链路
- 前端至少覆盖 `useSSE`、登录态恢复、项目页/工作台关键交互
- `useSSE` 至少覆盖：`meta -> token -> done` 正常流、仅 `heartbeat` 保活、首 `token` 延迟、`60s` 无数据超时、断流重连、`done` 后收尾状态
- 后端生成接口至少覆盖：正常流、慢速首包、异常中断、heartbeat 定时发送、代理后仍可逐块消费
- 浏览器级 E2E 至少覆盖：页面从“正在思考...”切换到流式内容，且不是在请求结束后一次性渲染

验证补充要求：

- 测试不是“有测试文件”就算完成，必须真的执行并记录结果
- 若暂时无法自动化，也必须提供手工黑盒验证清单和执行记录
- 任何 SSE 用例必须同时记录结构正确性和时序正确性；只验证字段、不验证到达时机，不能判通过
- 任何端到端“通过”结论必须注明访问地址、是否经过代理、是否为真实浏览器执行
- 对“流式接口正常”这类结论，必须附至少一条证据：事件时间线、浏览器截图、控制台日志或自动化断言输出

## 11. 本计划的使用方式

建议后续 AI 不要一次性处理整份计划，而是按以下节奏推进：

1. 先选一个阶段或一个模块
2. 由主执行 AI 完成检查、定位、修复
3. 修复后立即做最小自检
4. 再交由验证型 AI 做黑盒验收
5. 在计划文档中回填完成状态和验证结果

建议从以下顺序开始：

1. 阶段 A
2. 阶段 B2 + B3
3. 阶段 C5 + E5
4. 阶段 C6 + E7
5. 阶段 F

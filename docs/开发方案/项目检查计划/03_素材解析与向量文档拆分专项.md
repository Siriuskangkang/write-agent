# 素材解析与向量文档拆分专项

这个专项文档只解决一个问题：

上传的素材，应该如何被正确解析、切分、落库，并最终变成可检索、可生成引用的向量文档。

## 一、当前代码中的实际处理链路

根据现有实现，当前链路是：

1. 用户上传文件到 `source_files`
2. 文件进入 `file-parse` 队列
3. `ParseWorker` 按文件类型调用解析器
4. 解析器返回 `ParseResult`
5. `ParseWorker` 先写入 `documents`
6. 再调用 `ChunkService.createChunksForDocument()`
7. `ChunkService` 调用 `chunkDocument()` 生成 `chunks`
8. `ChunkService` 为每个 chunk 提取 `keywords` 和 `search_terms`
9. `embedding` 当前统一写成 `null`
10. `RetrievalService` 优先走关键词召回；只有存在 embedding 时才尝试语义召回

涉及代码：

- `backend/src/file/parse.worker.ts`
- `backend/src/file/parsers/pdf.parser.ts`
- `backend/src/file/parsers/docx.parser.ts`
- `backend/src/file/parsers/pptx.parser.ts`
- `backend/src/file/parsers/markdown.parser.ts`
- `backend/src/file/parsers/txt.parser.ts`
- `backend/src/chunk/chunker.ts`
- `backend/src/chunk/chunk.service.ts`
- `backend/src/retrieval/retrieval.service.ts`

## 二、正确的目标链路

一份素材要成为“正确的向量文档”，至少要完成以下 8 步：

1. 文件被正确识别类型，并落盘到可追踪的 `source_files`
2. 文件内容被解析为统一的 `Document`
3. `Document` 内部被切成结构稳定的 `sections`
4. `sections` 被进一步切成语义相对完整的 `chunks`
5. 每个 `chunk` 保留足够 metadata
6. 每个 `chunk` 被写入标准化检索字段
7. 每个 `chunk` 生成 embedding 并成功入库
8. 检索时能按 metadata 把命中的片段映射回原文件、页码、章节

如果其中任何一步不成立，这份素材都不能算“正确进入向量文档体系”。

## 三、当前实现与正确目标之间的主要缺口

### 1. embedding 实际未生成

当前 `ChunkService` 中把 `embedding` 固定写为 `null`。

这意味着：

- 语义检索事实上没有真正启用
- 检索当前主要依赖关键词和 `search_terms`
- “向量文档”目前只完成到了“可切块的检索文档”，没有完成到“可向量召回的文档”

### 2. 数据库迁移和实体定义疑似不一致

迁移脚本中 `chunks.embedding` 是 `vector(1536)`。

但实体里 `embedding` 定义为 `float[]`。

这会带来高风险：

- ORM 映射可能与真实数据库字段不一致
- 语义检索 SQL 使用 `<=>` 时依赖数据库里真的是 vector 类型
- 即使后续补了 embedding 生成，也可能因为字段类型不一致而不能正确写入或查询

### 3. 切块只有长度规则，没有重叠策略

当前 `chunkDocument()` 的规则是：

- 优先按 section 内段落切分
- `MIN_CHUNK_SIZE = 300`
- `MAX_CHUNK_SIZE = 800`
- 小块在特定条件下合并到上一块
- 没有 overlap

风险：

- 跨 chunk 的上下文丢失
- 章节边界附近的信息容易被截断
- 对大模型生成时的引用召回不够稳

### 4. 解析出的 section 质量依赖简单启发式

当前各格式解析特点：

- PDF：每页一个 section
- DOCX：用“短文本且不含句号”猜测标题
- PPTX：每页幻灯片一个 section
- Markdown：按 `#` 到 `###` 标题切 section
- TXT：按空行切 paragraph，再直接当 section

这意味着 section 质量并不稳定：

- PDF 会把同一章节拆散到多页
- DOCX 标题识别可能误判
- TXT section 可能过细，导致 chunk 过碎

### 5. 文件状态更新顺序存在风险

`ParseWorker` 当前在 `documents` 写入后、chunk 创建前，就把文件状态更新为 `DONE`。

风险：

- 一旦后续 chunk 创建失败，文件表面上已经是“解析完成”
- 但实际上 `chunks` 不完整甚至为空

### 6. 检索质量当前更偏“关键词检索”，不是“混合向量检索”

`RetrievalService.getQueryEmbedding()` 目前返回 `null`。

所以现状应被定义为：

- 有检索文档
- 有关键词召回
- 向量召回尚未真正落地

## 四、什么才算“正确拆分成向量文档”

以下标准必须同时满足。

### 4.1 解析层标准

- 每个文件都要产出一个 `Document`
- `Document.content_text` 不为空
- `Document.sections` 不能只是空数组
- `sections` 应尽量保留原始语义边界
- 能回溯 section 来自哪一页、哪一节、哪一张 slide

### 4.2 切块层标准

- chunk 不跨越完全无关的 section
- chunk 内部语义应尽量完整
- chunk 长度不能过短，也不能过长
- 小 chunk 合并必须有规则，不能随机拼接
- 最后一块不能因为过短而完全丢失
- 必须为每个 chunk 生成稳定的 `chunk_index`

### 4.3 metadata 标准

每个 chunk 至少要带：

- `project_id`
- `file_id`
- `document_id`
- `chunk_index`
- `content`
- `section_title`
- `page_number`
- `keywords`
- `search_terms`
- `embedding`

如果未来要增强引用质量，建议补充：

- `section_path`
- `heading_level`
- `source_file_name`
- `char_start`
- `char_end`

### 4.4 embedding 标准

- embedding 必须真实生成，不允许长期为 `null`
- embedding 维度必须和数据库字段一致
- 生成失败要有明确状态，不可静默忽略
- 重解析时旧 embedding 必须一起清理

### 4.5 检索回溯标准

- 命中 chunk 后，能回到原文件
- 能看到原 section 标题
- 对 PDF/PPTX 至少要能回到页码/页序
- 对引用链路要能提供足够稳定的来源信息

## 五、按文件类型的专项检查要求

### PDF

必须检查：

- 每页文本是否完整提取
- 页眉页脚、页码、重复文本是否过多污染内容
- 一页过长时 chunk 切分是否合理
- 跨页连续语义是否被严重割裂

边界情况：

- 扫描版 PDF
- 空白页
- 页数很多的大文件
- 单页超长内容

### DOCX

必须检查：

- 标题识别是否可靠
- 长段落是否被合理切块
- 多级标题是否丢失层级
- 表格、列表、编号是否被破坏成无意义文本

边界情况：

- 没有标准标题样式的 Word
- 很多短段落的文档
- 超长正文文档

### PPTX

必须检查：

- 每张 slide 是否正确提取文本
- 标题和正文是否被混成一条难以检索的文本
- 多个文本框的顺序是否可接受

边界情况：

- 文本很少的 slide
- 大量图表、图片、形状的 slide

### Markdown

必须检查：

- 标题层级是否保留
- 代码块、表格、列表是否污染 chunk 语义
- 标题过多时 chunk 是否过碎

### TXT

必须检查：

- 空行分段是否合理
- 是否出现“一段一个 section，导致过度碎片化”
- 长文本时 fallback 切块是否稳定

## 六、专项检查任务清单

### `A2` 主检查任务

1. 检查 `ParseResult` 是否对所有文件类型都稳定返回 `title/content_text/page_count/sections`
2. 检查 `ParseWorker` 的状态更新顺序是否正确
3. 检查 `documents.sections` 的结构质量是否满足后续切块需要
4. 检查 `chunkDocument()` 是否真的按语义段落而不是机械长度切割
5. 检查 `MIN_CHUNK_SIZE` / `MAX_CHUNK_SIZE` 是否适合中文教材场景
6. 检查是否需要增加 overlap
7. 检查 `keywords/search_terms` 是否足够支持检索
8. 检查 embedding 生成链路为何缺失，并补齐
9. 检查 `Chunk` 实体与 migration 的 embedding 类型是否一致
10. 检查重解析是否会清理旧 `documents/chunks/citations/embedding`

### `A4` 协同检查任务

1. 检查素材页是否能正确展示解析状态
2. 检查是否需要在前端显示“已解析但未完成向量化”的状态
3. 检查用户是否能查看解析结果、检索片段和来源信息

### `V1` 黑盒验证任务

1. 上传每种支持格式各一份样本文件
2. 验证每份文件都能产出 `documents`
3. 验证每份文件都能产出 `chunks`
4. 验证 chunk 的 `section_title/page_number` 是否合理
5. 验证重解析后旧 chunk 是否消失、新 chunk 是否生效
6. 验证检索能命中已上传素材中的关键内容
7. 若实现了 embedding，验证语义近义查询是否能命中

## 七、专项验收标准

以下条件同时满足，才能判定“素材已正确拆分成向量文档”：

1. 上传后的文件能稳定从 `source_files` 进入 `documents`
2. `documents.sections` 有稳定结构，不是空壳
3. `chunks` 数量合理，不明显过碎或过粗
4. `chunk` metadata 完整
5. embedding 已真实生成并可查询
6. 检索能根据 chunk 找回正确的文件、页码、标题
7. 重解析后数据一致，没有脏旧数据
8. 至少覆盖 PDF、DOCX、PPTX、MD、TXT 五种格式中的代表样本

## 八、当前优先修正建议

优先级建议如下：

1. 先修 `embedding` 未生成的问题
2. 核对 `Chunk` 实体与数据库 migration 的 embedding 类型不一致问题
3. 调整 `ParseWorker` 状态更新顺序，避免“已完成但无 chunk”
4. 再评估 chunk 长度、overlap、section 质量
5. 最后再做检索质量和召回质量优化
